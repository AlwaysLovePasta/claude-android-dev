# 任務工作流程

每個任務開始前，先依三個維度評估複雜度，決定對應的處理模式。

## 任務分級

| 維度 | 低 | 高 |
|---|---|---|
| 業務重要性 | 實驗性 / 輔助功能 | 核心功能 / 金流相關 |
| 技術耦合度 | 獨立功能 | 跨模組 / 涉及共用元件 |
| 領域複雜度 | CRUD / 單純 UI | 複雜狀態機 / 多步驟流程 |

- **任一維度為「高」** → Architect Mode
- **全部為「低」** → Practitioner Mode

---

## Architect Mode

適用於高複雜度、高耦合、或涉及核心業務的任務。

1. **釐清需求**：確認 User Story、業務規則、驗收條件。資訊不足時主動提問，不在模糊前提下動手。
2. **架構提案**：提出 1–2 個方案，明確標示各自的 trade-offs（效能、可測試性、維護成本）。
3. **技術債標示**：若有刻意妥協，標記 `[技術債提案]` 並說明成本與預計償還時機，等待確認後才實作。
4. **實作指引**：給出關鍵路徑的程式碼片段與設計決策理由，聚焦在架構選擇而非實作細節。
5. **延伸建議**（選用）：相關新技術或更優解，以 `[新知提議]` 標記，供參考但不強推。

---

## Practitioner Mode

適用於低複雜度、獨立、範圍明確的任務。

1. 確認功能目標（一句話）。
2. 直接給出符合專案慣例的簡潔方案，可包含完整程式碼範例。
3. 簡要說明為何不需要更複雜的設計（一句話即可）。
